**Главные дефекты:**

**Что нужно решить автору ТЗ:**

#### F-03 · Существенный · Размытая формулировка «в момент покупки» в цели

- **Требования:** R-01 (Цель)
- **Критерий:** Однозначность (`UNAMBIGUOUS`) · правило NFR-MEASURABLE
- **Где:** строки 23, 46
- **Цитаты из документа:**
  > «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.» — _строка 23_
  > «Сервис передаёт push на отправку в течение минуты после получения события.» — _строка 46_
- **Проблема:** Формулировка «в момент покупки» не содержит конкретного временного интервала и перцентиля, а также противоречит разделу нефункциональных требований, допускающему задержку передаче push до 1 минуты.
- **Чем опасно:** Невозможно однозначно подтвердить выполнение цели на этапе QA-приемки.
- **Как исправить:** Уточнить формулировку цели, соотнеся ее с NFR.
- **Предлагаемая формулировка:** _Дать клиенту возможность получать уведомление о достижении личного бюджета в течение [уточнить: 60] секунд после проведения покупки._
- **Проверка замечания:** цитаты найдены в документе; критик: подтверждено (Разногласие между формулировкой в цели («в момент покупки») и НФТ («в течение минуты»).)

### R-03 · (Процесс): Последовательность выполнения операций от покупки до отправки push.

> «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.» — _строка 34_

Оценка по критериям: **Полнота** — Не описаны альтернативные ветви процесса (порог не достигнут, опция выключена).; **Соответствие шаблону** — Отсутствует уникальный идентификатор требования.

#### F-05 · Существенный · Неполнота описания BPMN-процесса

- **Требования:** R-03 (Процесс)
- **Критерий:** Полнота (`COMPLETE`)
- **Где:** строка 34
- **Цитаты из документа:**
  > «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.» — _строка 34_
- **Проблема:** Схема процесса содержит только идеальный сценарий (happy path) и не описывает завершение процесса в случаях, если порог не достигнут или тумблер уведомлений отключен.
- **Чем опасно:** Риск потери альтернативных веток при проектировании архитектуры сервиса и составлении тест-кейсов.
- **Как исправить:** Дополнить описание процесса условием ветвления при недостижении порога или отключенном сервисе.
- **Предлагаемая формулировка:** _Проведение покупки → пересчёт расходов → проверка активности уведомления и достижения порога → если условие выполнено и push в текущем периоде не отправлялся, отправка push → завершение._
- **Проверка замечания:** цитаты найдены в документе; критик: подтверждено (BPMN описывает исключительно положительный сценарий и упускает ветвления.)

### Проверка критериев приёмки исполнением

Каждый критерий приёмки «исполнен» по правилам документа шаг за шагом; результат сравнён с ожидаемым в критерии.

| Критерий | По требованиям получается | В критерии ожидается | Итог |
| :--- | :--- | :--- | :--- |
| R-12 (Критерий приёмки 1) | Итог 50 000 ₸ и один push | Итог 50 000 ₸ и один push | **совпадает**. Расчёт суммы (48 500 + 1 500 = 50 000 ₸) и отправка 1 push при достижении порога полностью соответствуют правилам Ф-2 и Ф-3. |
| R-13 (Критерий приёмки 2) | Январский счётчик вырос на 4 000 ₸ | Февральский счётчик вырос на 4 000 ₸ | **РАСХОЖДЕНИЕ**. Согласно Ф-2 месяц определяется по дате совершения (31 января — январь), а не по дате проведения (1 февраля), поэтому должен увеличиться январский счётчик, а не февральский. |
| R-14 (Критерий приёмки 3) | Счётчик показывает 19 900 ₸ | Счётчик показывает 19 900 ₸ | **совпадает**. Перевод исключается из расчета расходов в соответствии с Ф-2, сумма расходов не меняется. |

## 5. Уточняющие вопросы к автору ТЗ

Вопросы, без ответа на которые нельзя однозначно реализовать или протестировать требования. Ответы можно вписать в файл `*.answers.yaml` рядом с отчётом и запустить агента повторно с флагом `--answers`: агент пересмотрит выводы.

**Q-01 · Высокий приоритет · кому: Product Owner / Бизнес-аналитик**

По какому правилу определяется месяц отнесения операции к расходам: по дате совершения покупки в Алматы (п. Ф-2) или по дате проведения/клиринга операции (Критерий приёмки №2)?

Варианты ответа: а) По дате совершения покупки клиентом (по Алматы); б) По дате фактического проведения (клиринга) операции; в) другое: уточните

_Почему важно:_ Противоречие между Ф-2 и критерием приёмки №2 приводит к неверному расчёту месячного бюджета и невозможности написать однозначные автотесты.

_Связано:_ F-01, R-05 (Ф-2), R-13 (Критерий приёмки 2)

**Q-02 · Высокий приоритет · кому: Product Owner / Бизнес-аналитик**

Отправляется ли повторный push в текущем месяце, если клиент изменил порог расходов, когда ранее по прежней настройке push уже отправлялся (п. Ф-3 заявляет «максимум один push в месяц», а п. Ф-4 — «независимо от истории предыдущей настройки»)?

Варианты ответа: а) Лимит 1 push в месяц строгий: повторный push не отправляется ни при каких условиях; б) Изменение порога сбрасывает лимит: при новом достижении отправляется ещё один push; в) другое: уточните

_Почему важно:_ Прямое противоречие двух бизнес-правил блокирует проектирование логики отправки уведомлений и тест-дизайн.

_Связано:_ F-02, R-06 (Ф-3), R-07 (Ф-4)

**Q-03 · Высокий приоритет · кому: Бизнес-аналитик**

Каково поведение системы, если клиент включает уведомление или изменяет порог в середине месяца, когда его расходы уже равны новому порогу или превышают его (п. Ф-1, Ф-4)?

Варианты ответа: а) Push отправляется мгновенно при сохранении настройки; б) Push отправляется только при совершении следующей покупки в этом месяце; в) Push не отправляется до следующего месяца; г) другое: уточните

_Почему важно:_ Не описан ключевой сценарий включения/изменения настроек «поверх» уже накопленной суммы расходов.

_Связано:_ F-08, R-04 (Ф-1), R-06 (Ф-3), R-07 (Ф-4)

**Q-04 · Средний приоритет · кому: Системный аналитик / Бизнес-владелец**

Как должны отражаться возвраты прошлых периодов (п. Ф-2 говорит «уменьшает расходы месяца исходной покупки»): корректируется ли закрытый прошлый месяц или сумма вычитается из текущего месяца?

Варианты ответа: а) Уменьшаются расходы текущего месяца (месяца проведения возврата); б) Корректируется прошлый месяц (без повторной отправки push); в) другое: уточните

_Почему важно:_ Изменение итогов закрытого периода может потребовать сложных перерасчетов, а в модель данных не добавлены атрибуты связи с исходной операцией.

_Связано:_ F-09, F-13, R-05 (Ф-2), R-10 (Данные)

**Q-05 · Средний приоритет · кому: Бизнес-владелец / Аналитик**

Какие типы операций и валюты входят в расчёт месячного порога (п. Ф-2): учитываются ли покупки в иностранной валюте (и по какому курсу), комиссии и квази-кэш?

Варианты ответа: а) Только покупки в KZT; комиссии и квази-кэш исключаются; б) Покупки в любой валюте по курсу на момент проведения + комиссии; в) другое: уточните

_Почему важно:_ Неполнота классификации операций приведет к расхождениям в расчете расходов между сервисом и клиентом.

_Связано:_ F-10, F-11, R-05 (Ф-2)

**Q-06 · Средний приоритет · кому: Архитектор / Информационная безопасность**

Какой HTTP-метод и способ передачи параметров должен использовать метод `/alerts/saveLimit` (Раздел REST API)?

Варианты ответа: а) Метод POST или PUT с передачей JSON-тела в Request Body; б) Метод POST с URL-encoded параметрами; в) другое: уточните

_Почему важно:_ Использование GET-метода для изменения данных с передачей параметров в URL нарушает стандарты REST API и создает риски безопасности.

_Связано:_ F-18, F-19, F-22, R-11 (Интеграция), R-15 (API Логика), R-17 (API Параметры)

**Q-07 · Средний приоритет · кому: Команда разработки / Архитектор**

Каким HTTP-кодом ответа должна сопровождаться ошибка валидации порога при запросе к API (Раздел REST API)?

Варианты ответа: а) HTTP статус 400 Bad Request; б) HTTP статус 200 OK с полем result: ERROR; в) другое: уточните

_Почему важно:_ Возврат ошибки бизнес-логики со статусом HTTP 200 OK (`{"result":"ERROR"}`) противоречит спецификации статусов 400 Bad Request.

_Связано:_ F-20, R-15 (API Логика), R-18 (API Ошибки)

**Q-08 · Средний приоритет · кому: Системный аналитик**

## 8. Итог

**Можно ли начинать разработку:** нет. **Можно ли начинать тестирование (тест-дизайн):** нет.

Документ содержит два критических противоречия в ключевой бизнес-логике (определение месяца операции для расчёта бюджета и правила отправки push при изменении порога), а также существенные ошибки в спецификации REST API и информационной безопасности. Начинать разработку и тестирование до устранения дефектов нельзя, так как реализация приведет к некорректным финансовым расчетам и переделкам.

Правило решения: есть критичный дефект → «нет»; есть только существенные → «условно»; только незначительные → «да» (`methodology/severity.md`).

**Что исправить в первую очередь:**

1. Устранить противоречие между Ф-2 и Критерием приёмки №2 (F-01): зафиксировать единый подход к определению месяца операции (по дате совершения или дате клиринга).
2. Устранить конфликт между Ф-3 и Ф-4 (F-02): четко определить, отправляется ли push при изменении порога, если в текущем месяце лимит push уже исчерпан.
3. Исправить REST API спецификацию (F-18, F-19, F-22): изменить HTTP-метод сохраняющего запроса `/alerts/saveLimit` с GET на POST/PUT, перенести параметры из Query в JSON Request Body.
4. Исправить обработку ошибок в API (F-20): при ошибке валидации возвращать корректный HTTP-статус 400 Bad Request вместо HTTP 200 OK с `result: ERROR`.
5. Дополнить правила расчёта расходов (F-08, F-09, F-12): описать сценарии включения опции в середине месяца, обработки возвратов прошлых периодов и повторных превышений порога.
6. Привести в соответствие единицы измерения и типы данных (F-15, F-21): унифицировать типы полей (integer/string) в API и единицы хранения денег (тенге/тиыны) в модели данных.
7. Заполнить метаданные документа и критерии приёмки для требований Ф-1 и Ф-4 (F-07, F-24).
