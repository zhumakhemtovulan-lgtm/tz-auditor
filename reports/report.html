FIN-IDEMPOTENCY описано Описана защита от двойного учета при повторной доставке события процессинга.
FIN-AUDIT описано Описан состав данных для хранения, достаточный для разбора операций и отправки уведомлений.
FIN-STATE описано Описано состояние выключено по умолчанию, сохранение накопленной суммы при изменении порога и поведение при включении.

NFR-MEASURABLE описано Срок передачи push измерим и имеет четкую точку отсчета.
API-STATUS описано Коды ответа (200, 201, 400, 401, 403, 404, 500) соответствуют результатам выполнения запросов.
API-CONTRACT описано Параметры запроса (cardId, amount, enabled) и типы данных описаны и согласованы в таблицах контракта.
DOC-TRACE описано Приведены критерии приемки, арифметически верные и опирающиеся на функциональные требования.
DOC-DATA описано Модель данных содержит необходимые поля для реализации логики.
DOC-ROLLBACK описано В чек-листе ревью зафиксировано наличие вариантов скрытия функционала при невозможности отката.

Q-02 · Высокий приоритет · кому: бизнес-владелец

Должен ли клиент получить повторный push в текущем календарном месяце, если после достижения порога и получения уведомления он изменил порог в большую сторону, а затем снова совершил покупку?

Почему важно: Без уточнения правила сброса лимита push-уведомлений при изменении порога невозможно спроектировать логику сервиса и избежать спама или потери важных уведомлений для клиента.

Связано: F-02, R-05 (Ф-3), R-06 (Ф-4), R-14 (Особые правила)

8. Итог

Можно ли начинать разработку: нет. Можно ли начинать тестирование (тест-дизайн): нет.

Разработку и тестирование начинать нельзя из-за наличия критических дефектов: выявлены прямые логические противоречия между требованиями Ф-3 и Ф-4, а также между правилом Ф-2 и критерием приёмки №2. Кроме того, зафиксированы грубые нарушения архитектуры REST API (использование GET для сохранения данных) и требования информационной безопасности.

Правило решения: есть критичный дефект → «нет»; есть только существенные → «условно»; только незначительные → «да» (methodology/severity.md).

Что исправить в первую очередь:

  1. Устранить противоречие в расчёте периода между правилом Ф-2 и критерием приёмки №2 (F-01).
  2. Разрешить противоречие между ограничением частоты push (Ф-3) и поведением при изменении порога (Ф-4) (F-02).
  3. Добавить требования по маскированию чувствительных данных (номера карт) в соответствии с правилами ИБ (F-03).
  4. Исправить REST API тип метода с GET на POST или PUT для операции сохранения настроек (F-04).
  5. Привести типы данных параметра enabled к единому типу в запросе и ответе (F-17).
  6. Добавить критерии приёмки для требования Ф-4 (F-07).
