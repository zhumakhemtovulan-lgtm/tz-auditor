# Шкала критичности дефектов

Аналог существенности в аудите: насколько дефект влияет на решение «можно ли начинать разработку и тестирование».

| Уровень | Код | Когда ставить | Примеры |
|---|---|---|---|
| Критичный | critical | Разработку или тест-дизайн нельзя начинать: противоречие между требованиями, непроверяемое ключевое требование, неверный расчёт денег, пропущено правило, без которого функция работает неправильно, риск для безопасности данных. | Требование и критерий приёмки дают разный результат; ошибка возвращается с кодом успеха; не определено, какая дата относит операцию к периоду. |
| Существенный | major | Можно начинать, но будут ошибки или споры в нестандартных сценариях; требование неоднозначно или неполно. | Не описан частичный возврат; срок без точки отсчёта и перцентиля; не описано включение функции в середине месяца. |
| Незначительный | minor | Оформление и гигиена документа, не влияющие на поведение системы. | Не заполнены версия, согласующие; опечатка; нет идентификатора у нефункционального требования. |

Калибровка:
- «Критичный» — только если без исправления **неверно работает бизнес-логика или деньги** (противоречие правил, неверный расчёт, неверное отнесение к периоду) либо есть **реальная утечка данных клиента** (номер карты, персональные данные в открытом виде).
- Нарушения стиля API (метод, коды ответа, формат), если функцию всё равно можно реализовать однозначно, — «существенный».
- Несколько замечаний об одной причине (например, один неверный HTTP-метод) — это один дефект, а не несколько.

Итоговое решение:
- есть хотя бы один критичный дефект → «нет» (начинать нельзя);
- критичных нет, но есть существенные → «условно» (начинать с оговорками, закрыть вопросы);
- только незначительные → «да».
